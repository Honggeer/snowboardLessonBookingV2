# v2 项目契约

本文件面向 AI 开发代理与项目决策者。MUST/必须、MUST NOT/不得是硬性规则；SHOULD/建议允许记录理由后作出局部取舍。适用于独立的 snowboardLessonBookingApp-v2 项目。v1 仅作为业务与代码参考，不得直接复制生产数据、凭证或旧依赖树。功能代码必须经过对应实施计划 review 后开始。

## 1. 产品与协作契约

| ID | 规则 |
|---|---|
| PROD-01 | 一个教练服务多个学员；保留学员注册、登录、自助预约及个人课程页面。 |
| PROD-02 | 教练可管理课程、排课、预约和学员档案。宣传视频与图片属于产品内容。 |
| PROD-03 | 多教练招募、教练审核、平台运营后台不进入默认 v2 范围；新增须由用户决定。 |
| WORK-01 | AI 负责实现、验证、文档维护及决策提案；用户主要负责业务、架构与成本取舍。 |
| WORK-02 | 用户提出新功能即授权需求分析和文档/计划编写；AI 必须先提交 ai-docs/implement-plan 中的具体计划让用户 review。只有用户明确同意相应计划后，才允许实现功能代码。 |
| WORK-03 | 未定业务规则和未批准计划阻塞依赖的功能实现；AI 可以继续只读分析、文档设计及已单独授权的其他任务，不得把等待时间或沉默当成批准。 |
| WORK-04 | 改变已确认技术/架构、引入实际付费资源、生产部署或不可逆数据操作，必须先确认现有授权是否覆盖；未覆盖时提交具体可审阅方案再确认。 |

| WORK-07 | Codex 不得自行执行 Git commit（含 amend）或 push。改动保留在工作区供用户 review，由用户自行 commit/push；仅用户明确要求 Codex 执行对应操作时例外。 |
| WORK-08 | 对未知或含糊的需求、业务规则及事实，先查用户指令、已批准计划、源码和可验证资料；仍不确定时向用户澄清，暂停依赖该答案的工作，不得将推测写为已确认事实或自行替用户决策。 |
| WORK-09 | 用户批准对应计划后，进入 IMPLEMENTING 阶段的开发工作必须先创建对应测试用例，实际运行并确认因目标行为缺失而失败（RED）；再实现并运行同一用例至通过（GREEN），执行适用回归检查。记录测试、命令、失败原因和通过结果；环境/测试错误不是有效 RED。需求分析和批准前的计划/文档工作不要求 RED/GREEN，也不得在批准前写该功能的测试或实现代码。 |
| WORK-10 | 所有 Git commit 标题采用 `type: description`：小写 type、英文冒号、一个空格、简短描述。常用 type 为 `feat`、`fix`、`docs`、`refactor`、`test`、`chore`、`build`、`ci`、`perf`、`revert`。此格式规则不改变 WORK-07 的提交权限。 |
| WORK-11 | 开发中发现尚未记录的待办、缺陷、遗漏或改进，在 `ai-docs/todo/` 按独立编号和模板建立 ticket、更新索引；写清来源、背景、问题与影响、期望结果和完成判定，不写实现方案。ticket 只是记录，不能替代功能文档、实施计划或用户批准；超出已批准范围时先完成相应 review。 |

## 2. 架构与部署边界

| ID | 规则 |
|---|---|
| ARCH-01 | 后端是一个模块化单体应用；模块内部采用 Ports & Adapters。业务模块不等于独立进程或独立云服务。 |
| ARCH-02 | domain 保存业务状态、不变量、值对象与领域事件；不得感知 Web、数据库、Spring 或 AWS。 |
| ARCH-03 | application 编排用例、授权上下文、事务与端口；不得包含 SQL、HTTP 请求处理或供应商 SDK 调用。 |
| ARCH-04 | adapter 将 REST、定时任务、MyBatis、SMTP、S3 等外部机制转换成端口调用或实现。 |
| ARCH-05 | 外层依赖内层；domain 不依赖 application/adapter，application 不依赖 adapter，入站 adapter 不直接调用出站 adapter。 |
| ARCH-06 | 必须显式区分 API DTO、用例输入/输出、领域对象与数据库记录；不得将数据库记录作为业务模型或直接返回前端。简单内部映射无需为了形式额外创建接口。 |
| ARCH-07 | 时间、ID、邮件、对象存储和持久化等真实外部依赖通过小而明确的端口隔离；不得机械地给每个类添加接口、空实现或多层转发。 |
| ARCH-08 | 首个 v2 后端骨架必须加入可执行架构检查，覆盖依赖方向、domain 外部依赖、模块 API 与循环依赖；可采用 ArchUnit。 |
| ARCH-09 | 架构测试必须扫描生产类并按稳定的违规身份分类追踪。新增违规先修复；确需暂留时，每条登记精确身份、具体理由、关联已批准计划/ADR 或 ticket、消除条件及代码旁的解释性注释，并将对应类别显式基线数字加 1。修复后删条目、数字减 1。测试须拒绝未登记、同数量替换、仅改数字、缺少理由及过期登记；例外不自行改变 ARCH/DEP 硬约束或计划 review 门槛。 |

初期部署单元：NGINX/前端静态文件容器、Spring Boot 容器、MySQL 容器，位于一台 EC2；通知执行器先属于同一 Java 应用。媒体存储与分发使用独立云能力。服务端构建在 CI 完成，EC2 拉取版本化镜像运行。

30 CAD 是预算目标而非已验证报价。新增云资源必须说明持续费用、区域、存储/请求/流量及清理方式。既有 t3.micro 是否满足容量须实测，不得把 swap 当成容量保障。首次迁移后的旧资源继续运行费用也必须计入。

## 3. 包结构与依赖规则

新项目按业务模块组织；建议包根 `com.geer.snowboard.v2`，在工程底座计划批准后采用；不得把全局 `controller/service/mapper` 目录作为 v2 主结构：

```text
com.geer.snowboard.v2
├── bootstrap/                         # Spring 启动、Bean 装配、基础配置
├── identity/
├── students/
├── catalog/
├── scheduling/
├── bookings/
│   ├── domain/                         # 纯 Java 模型、规则、领域事件
│   ├── application/
│   │   ├── port/in/                    # 已发布用例接口及 command/query/result
│   │   ├── port/out/                   # repository、跨模块协作等出站端口
│   │   └── service/                    # 用例实现与事务边界
│   └── adapter/
│       ├── in/web/                     # REST、请求/响应 DTO、映射
│       ├── in/job/                     # 调度/批处理入口
│       ├── out/persistence/            # MyBatis mapper、DB record、repository 实现
│       └── out/module/                 # 调用其他模块发布用例的适配器
├── notifications/
├── media/
└── sharedkernel/                       # 极少量稳定的共同类型
```

- **DEP-01**：domain 与 `application.port` 必须保持纯 Java；可依赖 JDK 及经过记录的 sharedkernel 稳定类型。不得引入框架/序列化/校验注解、MyBatis mapper 或供应商类型。
- **DEP-02**：`application.service` 默认允许 Spring 的 `@Service` 与 `@Transactional`，作为明确的务实折中；不得使用 Servlet、Spring MVC、安全框架的全局上下文、JDBC、MyBatis 或 AWS SDK。更多框架依赖须有 ADR。
- **DEP-03**：控制器/任务入口构造已验证的 actor context、command/query，再调用入站端口；用例通过参数获得当前用户，不读取 ThreadLocal 或 Servlet 请求。
- **DEP-04**：跨模块只能调用该模块明确发布的 `application.port.in` 用例或订阅公开事件。不得引用其 domain、service、出站端口或 mapper。消费模块用自己的出站端口和 `adapter.out.module` 隔离协作。
- **DEP-05**：文档中声明数据表归属。模块不得直接读写其他模块业务表；确有需求的跨表只读报表必须记录目的、SQL、权限和边界例外，写操作仍由所属模块完成。
- **DEP-06**：禁止循环模块依赖；通过单向用例协作、事件或责任调整消除循环。共享包不得成为任意业务逻辑的容器。
- **DEP-07**：测试替身实现与生产适配器遵循相同端口；核心规则应能在没有 Spring、MySQL、SMTP、S3 的环境下测试。

## 4. 数据、预约与时间契约

| ID | 规则 |
|---|---|
| DATA-01 | Flyway 已合并/应用迁移 append-only；不得修改/删除已有版本或启用生产 schema 自动重建。v2 从独立数据库和自己的迁移链开始；导入 v1 数据必须有经过 review 的独立迁移计划。 |
| DATA-02 | 金额使用 BigDecimal / MySQL DECIMAL，显式保存币种；不得使用 float/double 表示业务金额。历史预约保存成交价格和必要课程快照，不依赖当前模板重算历史。 |
| DATA-03 | 时间点使用明确的 UTC/Instant 语义；业务日期、当地时间与 IANA 时区分别建模。JSON 时间点带偏移；仅表示日历日期的值不得用 UTC 转换截断。明确夏令时不存在/重复时间的策略。 |
| BOOK-01 | 预约状态变化通过具名用例和领域规则进行，文档列出允许转换、操作者、前置条件、副作用；不得开放任意 status 更新接口。 |
| BOOK-02 | 排课占用必须在 MySQL 事务中获得并发保障；`@Transactional`、先查后写或 JVM 锁单独使用均不足以保证正确性。 |
| BOOK-03 | 固定时段锁定稳定存在的占用/时间段记录，检查后原子更新；确认、取消、改期等竞争路径必须遵循一致锁协议。跨时段/同日地点规则需更大的协调范围。 |
| BOOK-04 | 设计唯一约束、条件更新或明确锁策略，并写明 isolation、锁顺序、重复请求与死锁处理；不能把所有 bookings.availability_id 设为唯一来偷偷禁止多个待确认申请。 |
| BOOK-05 | 有容量约束的多人课程需按容量设计，不得未经决定套用一对一模型。时间区间采用明确边界语义，例如 [start,end)。 |
| BOOK-06 | 改期必须原子地获取新占用、更新预约、释放旧占用，并让旧提醒失效；任何失败不得留下半完成的预约。 |
| BOOK-07 | 关键写入定义幂等行为，至少覆盖网络重试/重复点击；幂等键有作用域、请求指纹和唯一性，同键不同请求不得静默复用。 |

## 5. 身份、API 与前端契约

- **SEC-01**：服务端根据认证身份执行资源授权。学员仅可读取/修改允许操作的本人课程与资料；客户端 userId/studentId/role 不是授权证据。
- **SEC-02**：v2 身份路径使用 Spring Security；目标是服务端会话 + Secure/HttpOnly/SameSite Cookie。Cookie 写请求配置明确的 CSRF 防护。不得增加 localStorage 中的认证密钥使用。迁移及用户重新登录影响须写入功能文档。
- **SEC-03**：控制器不能作为唯一授权边界；业务用例验证 actor 对目标资源的权限。测试必须覆盖未登录、错误角色、其他学员资源。
- **API-01**：前后端独立构建，生产默认通过同源 `/api` 访问；不得让前端直接访问数据库或持有 AWS 长期凭证。
- **API-02**：v2 API 必须文档化 method/path、身份、输入/输出、业务错误及 HTTP status。现有 `{code,data,msg}` 是 v1 事实，不自动成为新接口规范；v2 响应/错误格式由第一项 API 计划决定并统一执行。
- **API-03**：新接口正确区分 400/401/403/404/409 等语义；403 不应默认清除有效会话。不得用通用成功响应吞掉失败。
- **API-04**：公开 DTO/用例契约不得泄露数据库记录、密码、令牌、堆栈或内部供应商错误。分页、过滤、排序有边界。
- **FE-01**：v2 新页面/行为明确空状态、加载、失败、重试和重复提交；缓存需包含用户作用域并在登出时清理，不得跨账号复用私人课程数据。
- **FE-02**：先读取实际 package.json 与现有工具，版本升级需检查兼容性并记录理由；不得把“最新/热门”当成替换库的唯一依据。

## 6. 通知与媒体契约

- **ASYNC-01**：需要随业务可靠发生的通知，业务变更与 outbox/通知任务在同一事务提交；不得在持有业务事务锁时发送邮件或调用云服务。
- **ASYNC-02**：任务保存在 MySQL，记录状态、尝试次数、下次执行时间、错误及领取信息；失败不能标记已发送。进程重启后可恢复。
- **ASYNC-03**：领取任务有原子保障和过期回收；限定批量、重试、退避和最终失败处理。按 at-least-once 设计，明确去重及“发送成功但写回失败”可能重复的处置，不能宣称 exactly-once。
- **ASYNC-04**：发送前检查预约状态/版本与提醒有效性；取消、改期或停用不得继续使用过期任务。耗时任务有专用有界执行资源，不得占满 HTTP 线程池。
- **MEDIA-01**：文件内容放对象存储，MySQL 保存归属、object key、大小、内容类型、用途与状态；不得把视频放数据库或当成 EC2 本地永久文件。
- **MEDIA-02**：教练通过后端授权获取有时效的上传凭证，浏览器直传；签发与发布均验证权限。大小/类型/配额通过合适策略与上传后检查落实，不能声称预签名 PUT 自动限制大小或一次性使用。
- **MEDIA-03**：上传与发布分离，完成后确认 object 存在且符合预期；未完成、非法及孤立上传有清理策略。宣传内容与学员私有教学资料分开授权。
- **MEDIA-04**：媒体经 CloudFront 分发，S3 bucket 保持私有并使用 OAC；公众可看宣传内容不等于 bucket 公开。第一版上传预处理好的视频，转码服务为另行决策。

## 7. 运维与交付契约

- **OPS-01**：数据库不发布到互联网；容器内网访问；应用使用专用数据库账号，不使用 root。生产密钥不得写入 Git、镜像、文档或测试输出。
- **OPS-02**：规划以 EC2 IAM Role 获取云权限，CI 使用 OIDC 临时凭证；不得把 v1 的长期凭证复制到新项目。
- **OPS-03**：镜像使用提交 SHA/明确版本；有健康检查、重启策略、日志轮转及上一版本恢复方式。单机接受短暂部署中断，不能描述为高可用或零停机。
- **OPS-04**：持久化卷不是备份。明确备份频率、保留时间、异机存储和恢复验证；灾难恢复目标由用户决定，每次演练记录恢复结果。
- **OPS-05**：新后台任务、日志、存储和云资源须说明资源上限与成本影响。AWS Budgets 提醒不等于硬性费用上限；不得承诺预算绝不会超出。
- **OPS-06**：生产部署、生产迁移、备份恢复操作应按实际授权执行；本文件不默认授权外部发布。

## 8. 每项功能的文档与 review 流程

1. 读取根 AGENTS.md、本契约、相关 ADR、已有功能/计划与源码。
2. 分配唯一功能 ID `NNNN`：在 `ai-docs/features/` 创建功能契约，在 `ai-docs/implement-plan/` 创建同 ID 实施计划；分别使用对应模板，两个索引同时更新。
3. 功能文档说明需求、业务规则、模块/端口、API/数据契约与验收；计划说明具体步骤、预计文件、检查、风险、成本、回退和用户决策。先做足以形成可审阅方案的只读调查，不提供空泛计划。
4. 待 review 时两份文档标记 AWAITING_REVIEW。将计划链接及需要决定的问题交给用户，停止未授权的依赖实现；继续文档或已单独批准的工作。
5. 用户明确同意后，在计划的审批记录填写日期、用户原话/可定位消息、批准修订号、范围与条件；两份文档进入 APPROVED。不得凭沉默、时间或 AI 自己判断写入批准。
6. 开始实现进入 IMPLEMENTING；先创建测试用例并执行有效 RED，再修改实现至 GREEN，运行适用回归检查；依据计划逐项更新 checkbox、实际文件和红绿测试证据。新发现的工作按 WORK-11 记录 ticket；实质范围变化增加 revision、撤销对新修订的批准并重新 review；不改变契约的局部实现细节只记录理由。
7. 实现完成更新到 IMPLEMENTED；必要检查全部通过、验收证据齐全后进入 VERIFIED。失败、缺少环境或未完成验收不能跳级。
8. 获得部署授权、完成发布并验证后进入 RELEASED；批准实现计划不自动授权生产部署或新增付费资源。
9. 同步功能文档、计划、两个索引、相关 ADR；最终交付链接、结果与未解决事项。

状态：DRAFT → AWAITING_REVIEW → APPROVED → IMPLEMENTING → IMPLEMENTED → VERIFIED → RELEASED；也可 REJECTED / CANCELLED。状态依据见两个目录的 README。项目文档骨架记录 0000 已验证；工程底座 0001 revision 2 已获用户批准并按实际证据更新状态。

一个业务功能跨前后端共用一个功能 ID、功能文档和实施计划；迭代更新原文件。影响行为的修复使用对应功能计划的修订或新独立计划，先 review 后改代码。纯拼写、格式、文档更新可在用户授权内维护原记录，不制造无意义的功能文件。

## 9. 完成标准与验证门禁

文档 MUST 有对应验收证据；不得将“写了测试”“CI 将会检查”“已有测试数量”当成实际通过。

已批准计划进入 IMPLEMENTING 后，开发工作按 WORK-09 记录测试先行的 RED/GREEN 证据；仅有最终通过结果不足以证明测试先行。测试无法运行时记录阻碍并处理，不得宣称完成 GREEN。

| 变更 | 必需验证 |
|---|---|
| 新 v2 后端骨架/模块 | 编译、架构依赖规则、模块无循环、领域可独立测试。 |
| 领域规则/状态/金额 | 对业务不变量与禁止状态转换的单元测试。 |
| SQL、锁、约束、迁移 | 使用真实 MySQL 的集成测试（可用 Testcontainers）；与目标生产版本匹配。锁/预约保障须有独立事务并发测试，不能只 mock mapper 或仅用 H2。 |
| 授权/API | API 契约、未登录/错误角色/资源越权测试。 |
| 异步任务 | 重试、任务失效、重复执行、进程中断或领取过期恢复的适用验证。 |
| 前端行为 | 实际构建与相关交互测试；关键端到端流程在加入可运行环境后验证。纯样式/文案调整通常无需新增测试。 |
| 部署/备份 | 配置校验、健康检查、版本恢复或实际备份恢复证据，按影响选择。 |
| 文档 | 内部链接、规则一致性、状态/索引与实际结果匹配。 |

工程底座已有 Maven 后端测试、前端 test/typecheck/build/lint、架构与真实 MySQL 测试、本地 Compose 冒烟检查。执行方式见各目录 README，实际结果见 0001 计划；这些检查不代表业务功能或生产部署已完成。测试环境缺失须记录原因并修复或明确受限交付，不得报告验证成功。

## 10. 演进、例外与事实来源

- 新项目独立开发、独立 Git 仓库；v1 保持原状。复用其业务资产以逐项经过 review 的功能实现，不能批量搬入旧全局三层结构。
- v2 使用独立本地数据库与配置。将来切换生产时有独立计划，明确 v1/v2 路由、数据与任务的唯一责任方，避免重复通知。
- 技术版本、云费用和兼容性以实际配置及最新官方资料为准；升级理由与真实验证结果写入功能文档。
- 例外需写出规则 ID、理由、范围、风险、撤销条件；涉及改变已确认决策的例外由用户 review 并写 ADR。
- 本契约由用户决策、AI 维护。变更更新版本与日期，同时同步入口、ADR、功能文档、实施计划和适用检查。
